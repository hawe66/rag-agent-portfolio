## 2. 3주차 Baseline 회고 (선결)

> 산출물: `docs/week4_retrospective.md` 의 첫 섹션

### 2.1 잘못 검색된 chunk 사례 발굴 (최소 2개)

3주차 baseline에서 평가 질문 셋을 다시 돌리되, 이번엔 검색된 chunk를 **눈으로 본다**. 정성 분석.

각 잘못된 사례마다 다음 형식으로 기록:

```markdown
### 사례 #1
- 질문: "..."
- 검색된 chunk (top-1 또는 잘못 들어간 chunk):
  - source: ...
  - page: ...
  - 내용 요약: ...
- 정답 chunk (있어야 할 chunk):
  - source: ...
  - page: ...
  - 내용 요약: ...
- 왜 잘못 검색됐다고 생각하는가 (가설):
  - 예: 청크 경계가 단계 중간을 끊었음 / 표 데이터가 노이즈로 작용 / 머리말이 모든 청크에 반복되어 유사도 왜곡 등
```

**팁:** 가장 가치 있는 사례는 "단계 중간에서 잘린 청크", "여러 모델 매뉴얼이 섞여 잘못된 모델의 청크가 top-k에 들어옴", "사양표 같은 정형 데이터가 자연어 질문과 안 맞는데도 매칭됨" 같은 도메인 특이적 실패.

### 2.2 데이터 전처리 관점 개선 가설 (1~2개)

§2.1 사례에서 도출한 개선 방향. 예시 형식:

```markdown
### 개선 가설 A
- 관찰: 청크 경계가 단계 중간을 자주 끊는다
- 가설: 매뉴얼의 "단계 번호 (1., 2., ...)" 또는 헤더를 separator로 인식하는 splitter를 쓰면 단계 단위로 의미 보존이 가능할 것
- 검증 방법: 4주차 전략 C에서 시도

### 개선 가설 B
- 관찰: 머리말("LG 코드제로 사용설명서") + 페이지 번호가 모든 페이지 상단에 반복됨
- 가설: 전처리 단계에서 머리말/페이지 번호 제거 시 의미 임베딩 품질 향상
- 검증 방법: §3에서 노이즈 제거 후 splitter 적용 비교
```

## 3. 데이터 품질 진단

> 산출물: `notebooks/week4_data_analysis.ipynb`

### 3.1 문서 구조 특성 파악 (도메인 특화 항목 추가)

스터디 가이드의 일반 항목 + 본 도메인(LG 가전 매뉴얼) 특화 항목.

**일반 항목:**
- 표 존재 여부 및 빈도 (사양표, 트러블슈팅 표 등)
- 이미지 존재 여부 (이번 주차에는 텍스트만 다루지만 위치/빈도는 기록 — Phase 2 입력)
- 헤더 / 섹션 구조 (안전주의 / 설치 / 사용 / 유지보수 / 문제해결 / 사양)
- footnote, 각주
- 메타데이터 (모델명, 발행일 등이 PDF 안에 명시되어 있는가)

**도메인 특화 항목:**
- 단계 번호 패턴 (예: "1.", "①", "STEP 1" 등 — 어떤 형식인가)
- 부품/도구 이름 등장 빈도 (가전 매뉴얼은 부품명이 핵심 entity)
- 같은 매뉴얼 안에 여러 변형 모델이 같이 다뤄지는가 (예: "WD325AS / WD325AW 공통")

### 3.2 노이즈 요소 식별

- 머리말 / 꼬리말 (모든 페이지에 반복되는 텍스트)
- 페이지 번호
- 광고성 문구 (제품 홍보, A/S 안내 반복)
- 중복 문장 (안전주의가 여러 페이지에 반복되는 패턴 등)
- 표가 텍스트로 깨져 들어온 경우의 의미 없는 문자열

식별 결과는 표로 정리:

```markdown
| 노이즈 유형 | 등장 빈도 | 영향 정도 | 처리 방안 |
|---|---|---|---|
| 머리말 (모델명+제품군) | 모든 페이지 | 중 | regex 제거 |
| ... | ... | ... | ... |
```

### 3.3 문서 길이 분포 시각화

- 매뉴얼별 페이지 수, 추출된 텍스트 토큰 수 (tiktoken으로)
- chunk_size=1000 기준 청크 개수
- 최소 / 최대 / 평균 / 표준편차
- **시각화 1개 이상**: 매뉴얼별 토큰 수 막대그래프 또는 청크 길이 히스토그램

> 발표용으로도 쓸 시각화. 깔끔하게 만든다.

## 4. Chunking 전략 비교 실험

> 산출물: `notebooks/week4_chunking_experiments.ipynb`

### 4.1 실험 설계 원칙

- **변수 통제**: chunking 외 모든 것 고정
  - 같은 PDF 코퍼스
  - 같은 embedding 모델
  - 같은 retriever (similarity, k=5)
  - 같은 prompt
  - 같은 평가 질문 셋
  - 같은 LLM
- **재현 가능성**: random seed 고정 가능한 부분은 고정. 사용한 모델 버전, 하이퍼파라미터 모두 기록.

### 4.2 전략 A: Baseline (3주차 설정 그대로)

- `RecursiveCharacterTextSplitter`
- `chunk_size=1000`, `chunk_overlap=200`
- 3주차 점수를 그대로 사용해도 되지만, **PDF 코퍼스나 평가 셋이 변동되었다면 재측정** (변수 통제 원칙)

### 4.3 전략 B: 파라미터 변경

같은 splitter, 파라미터만 변경. **최소 2개 변종 시도**:
- B1: 작은 청크 (예: `chunk_size=500`, `chunk_overlap=100`)
- B2: 큰 청크 (예: `chunk_size=1500`, `chunk_overlap=300`)

**작은 청크 가설**: 검색 정밀도 ↑, 문맥 부족 ↓
**큰 청크 가설**: 문맥 풍부 ↑, 검색 정밀도 ↓ / 청크 안에 노이즈 ↑

### 4.4 전략 C: 도메인 특화 splitter

**선택 가이드 (본 도메인 기준):**

LG 가전 매뉴얼 PDF는 (a) 명확한 섹션 구조 (b) 단계 번호 (c) 표/그림 인덴팅을 가짐. 후보:

- **(C1) Document-specific splitter** — `MarkdownHeaderTextSplitter` 등은 매뉴얼이 markdown이 아니라 부적합. PDF용은 LangChain 기본에 강한 게 없음
- **(C2) Custom separator** — `RecursiveCharacterTextSplitter`의 `separators` 인자를 도메인 맞춤으로 (예: 단계 패턴 `["\n\n", "\n1.", "\n2.", "\n①", "\n②", ".", " "]`)
- **(C3) Layout-aware loader + splitter** — `PDFPlumberLoader` / `Unstructured` 등으로 레이아웃 정보 살린 후 섹션 단위 분할
- **(C4) Header/Section 기반 후처리** — 추출된 텍스트에서 정규식으로 섹션 식별 후 섹션 단위 청크

**추천 우선순위:** C2 또는 C4 — 구현 난이도가 낮고 도메인 정보가 직접 반영되어 효과 확인이 빠르다. C3는 도전 과제로 보류 가능.

**§2.2의 개선 가설이 C 선택과 직결**: 가설에서 "단계 단위 분할이 효과적일 것"이라고 했다면 C2 또는 C4가 그 가설의 직접 검증이 된다.

> **선택 reasoning은 발표용 산출물에 그대로 사용된다 (§10).** "왜 이걸 선택했는가"가 면접 핵심 질문 — 한 단락 잘 써둘 것.

### 4.5 비교 결과 표

```markdown
| 전략 | chunk_size | chunk_overlap | 청크 개수 | Faithfulness | Answer Relevancy | Context Precision |
|---|---|---|---|---|---|---|
| A (baseline) | 1000 | 200 | ? | ? | ? | ? |
| B1 (작은 청크) | 500 | 100 | ? | ? | ? | ? |
| B2 (큰 청크) | 1500 | 300 | ? | ? | ? | ? |
| C (도메인 특화) | - | - | ? | ? | ? | ? |
```

### 4.6 정성 분석 동반 (수치만 보지 않는다)

각 전략에서 동일 질문 1~3개에 대해 **실제 검색된 top-3 chunk 비교**. 어떤 차이가 점수 차이를 만드는가를 눈으로 본다.

### 5.1 메타데이터 스키마 갱신

`WEEK3_TASKS.md §3.2` 의 스키마를 확장한다. 최소 2개 이상의 필드 추가.

**확장 권장 필드 (이번 주차에 채워보기):**

```python
{
    # 기존 (WEEK3)
    "source": "vacuum_complex_AX920BWE.pdf",
    "category": "vacuum",
    "complexity": "complex",
    "model_name": "AX920BWE",
    "page": 12,
    "chunk_id": "AX920BWE_p012_c003",

    # 새로 추가 (WEEK4)
    "section": "사용",                       # 안전주의/설치/사용/유지보수/문제해결/사양
    "has_table": False,                       # 청크 내 표 데이터 포함 여부

    # Phase 2 확장 자리 (그대로 비워둠)
    "step_number": None,
    "image_ids": [],
}
```

> `section`은 §3에서 식별한 헤더/섹션 구조를 활용해 자동 부착. 안 되면 수동/휴리스틱.

벡터 스토어에서 청크 1~2개 출력해서 메타데이터가 잘 들어갔는지 확인. 코드 한 셀이면 됨.

### 10.2 발표용 정리물 출력 형식
